## 2. Матрица «frontend → API → SQLite → frontend»

Для каждой строки Человек 2 выполняет действие в браузере с открытым Network,
эта роль сверяет JSON ответа и повторный GET/запись БД. Человек 1 исправляет
расхождения API. В основном UI **пока ни одна строка не подтверждена HTTP-вызовом**.
Подготовленные backend-тесты покрывают endpoints отдельно.

| Проверено из UI | Endpoint и метод | Событие / требуемый результат |
|---|---|---|
| [ ] | `POST tasks.php` | «Продолжить» после черновика → 201, сохранить реальный `task_id` |
| [ ] | `GET tasks.php`, `GET tasks.php?id=…` | Загрузка списка/возврат к черновику → данные из SQLite |
| [ ] | `POST cards.php`, `action:questions` | Получить ≥3 вопроса, связать ответы с `field`; карточка ещё не создаётся |
| [ ] | `POST cards.php`, `action:build` | Собрать одну карточку из семи ответов → 201, `card_id`, рейтинг 0 |
| [ ] | `GET cards.php?id=…` | Открыть созданную карточку вместе с подтверждениями и `rating_details` |
| [ ] | `POST cards.php` без action | Ручное создание карточки с 11 полями, если такой экран входит в поставку |
| [ ] | `PATCH cards.php` | Сохранение поля → текст, confirmed, рейтинг, уровень и расшифровка на экране |
| [ ] | `GET/POST questions.php` | Совместимый локальный режим вопросов: проверить отдельно task_id/card_id, причины `empty/not_confirmed/review` |
| [ ] | `POST generate.php` | Совместимый локальный режим сборки с метаполями: проверить отдельно; не вызывать вдобавок к `action:build` |
| [ ] | `PATCH publish.php` | Явная кнопка после просмотра → published=1; снятие → published=0 |
| [ ] | `GET catalog.php` | Открытие, фильтры и сортировка → серверный список опубликованных карточек |
| [ ] | `GET teams.php`, `POST teams.php` | Список и создание профиля → сохранить числовой `team_id`, отдельное поле technologies |
| [ ] | `POST proposals.php` | «Отправить предложение» → идея/план/ссылка/дата записаны, `pending`, `chosen=0` |
| [ ] | `GET proposals.php?card_id=…` | Бизнес видит предложения именно своей открытой карточки; команда видит обновлённый статус |
| [ ] | `PATCH choose.php` | Только клик бизнеса «Выбрать», «Отклонить» или «Отменить решение» → изменение одного proposal_id |
| [ ] | `OPTIONS` endpoints | Служебный CORS preflight, если используются разные origins; на одном origin отдельной кнопки не требуется |

Для альтернативного маршрута без UI зафиксировать «не используется в поставке»
и результат отдельного API-теста, а не ставить отметку «вызван из frontend».
Не нужно вызывать каждый альтернативный endpoint в одном действии пользователя.
Перед сдачей на каждый endpoint должно быть явное решение: UI-событие либо
документированный совместимый маршрут с отдельной проверкой.

## 3. Согласование форматов

| Сейчас в frontend | Backend | Требуемое преобразование |
|---|---|---|
| `industry` | `topic` | Тема карточки; поиск API не ограничен точным совпадением отрасли |
| `data`, `result`, `success` | `data_materials`, `expected_result`, `success_criteria` | Маппинг ключей вопросов и ответов |
| `contact`, `format` | `business_contact`, `interaction_format` | Роль/отдел и консультации; формат — отдельное метаполе |
| `score`, текстовый уровень UI | `rating`, `readiness_level` | Брать из ответа, отображать названия по таблице README |
| `taskId`, `t…` | числовые `task_id` и `card_id` | Хранить оба id; proposal привязывается к карточке |
| `idea`, `timeline`, `url` | `solution_idea`, `deadline`, `prototype_link` | Конкретная дата YYYY-MM-DD; HTTP/HTTPS или пусто, не `#` |
| «На рассмотрении», «Выбрана», «Отклонена» | `pending`, `accepted`, `rejected` | Статус интерфейса из серверного ответа |

- [ ] Сохранять редактируемый текст с `confirmed:0`; повышение рейтинга — после
  явного подтверждения с `confirmed:1`. Не полагаться на значение по умолчанию PATCH.
- [ ] После `action:build` задать `title/topic/need/interaction_format` отдельными
  PATCH перед публикацией; семь полей AI JSON не расширять метаданными.
- [ ] Отображать ошибки 400/404/409/422/500/502, сохранять ввод, разрешать исправление.
- [ ] Пока запрос выполняется, блокировать повторную отправку создания/публикации/
  отклика. Повторный POST создаёт новую запись: идемпотентность API не обещает.
- [ ] Не показывать «сохранено/выбрано» до успешного ответа; после неуспеха не оставлять
  локальное состояние, которого нет в SQLite.
- [ ] Выводить пользовательский текст как текст, не исполнять HTML/JS из ответа.

## 7. Два полных прогона перед сдачей

Каждый **браузерный** прогон: новая задача → ≥3 вопроса → ответы → редактирование →
подтверждения 0…100 → ручная публикация → каталог/фильтры → два отклика → сравнение →
ручное решение → просмотр статуса второй ролью. Сверять Network и повторный GET;
достаточно нового уникального названия, очищать рабочую базу не нужно.

## 8. Критерий готовности к сдаче

Два успешных браузерных прогона и отсутствие открытых ошибок основного сценария;
формула UI совпадает с backend; низкий рейтинг не ограничивает каталог; fallback
прозрачен; выбор происходит только явным действием в UI. README, DEMO и API.md
соответствуют фактической версии. Совместимые неиспользуемые endpoints обозначены,
а не скрыты под фиктивными отметками о frontend-интеграции.

Текущие два backend-прогона — подтверждение исправности API, **не разрешение
отмечать два сквозных браузерных прогона выполненными**.
