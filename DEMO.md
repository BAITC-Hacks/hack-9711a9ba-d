# AI Sana: демонстрация на 5 минут

Цель — показать одну задачу от слабого черновика до ручного решения бизнеса
в приложении. Основание: разделы 9 и 11 кейса HackAlem AI, страницы 5–6.
Веса критериев ниже взяты из кейса; это не обещанная оценка жюри.

**До защиты:** закрыть [INTEGRATION_CHECKLIST.md](INTEGRATION_CHECKLIST.md), подключить
frontend к API и дважды пройти сценарий в браузере. Сейчас UI на LocalStorage;
план описывает целевую интегрированную защиту, а не уже выполненный UI → SQLite показ.

## Подготовка до таймера

- Запустить проект по README, проверить Console/Network; подготовить две вкладки
  или профиля браузера: бизнес и команда, с общей SQLite через API.
- Проверить пять задач, карточек, команд и предложений в демо-наборе. Не удалять
  рабочую базу ради репетиции; новые прогоны выполнять на новых задачах.
- Подготовить тексты ниже для вставки, два профиля команды и настоящие доступные
  ссылки на демонстрируемые прототипы; сроки сверить с датой защиты.
- Открыть промпт в `ai_helper.php`, примеры JSON в `AI_HELPER.md` и результат
  проверки некорректного ответа API для пояснения режима и вопросов жюри.
- Для стабильного показа отключить `AI_API_KEY` и перезапустить PHP. Честно назвать
  режим «локальная заглушка»: кейс допускает его при показе контракта и ошибок.
- Назначить ведущего бизнеса и оператора команды. Второй оператор отправит второе
  предложение **вручную на ту же новую карточку** после её публикации.

## Один подготовленный пример

Слабый черновик: **«Нужен прогноз продаж кафе».** Название: «Прогноз спроса на выпечку».
Тема: `HoReCa`; потребность: «Сократить списания выпечки»; формат: «Онлайн».
Детали ниже — синтетические **ответы бизнеса**, вводимые человеком, а не факты,
которые модель должна придумать из короткого черновика.

| Поле | Ответ бизнеса |
|---|---|
| `context` | В кафе каждый вечер остаётся выпечка. Сейчас списания записываем вручную. Нужно точнее планировать закупки. |
| `data_materials` | Есть обезличенная CSV-таблица продаж за 6 месяцев: дата, товар, количество продаж и списаний. |
| `expected_result` | Нужен прототип прогноза спроса на следующий день с таблицей рекомендуемого объёма закупки. |
| `success_criteria` | Снизить списания на 20% за месяц пилота, сохранив доступность популярных товаров не ниже 95%. |
| `constraints` | Прототип за 3 недели. Только обезличенные данные. Подключение к кассе в пилот не входит. |
| `users` | Управляющий кафе проверяет прогноз и составляет заказ поставщику. |
| `business_contact` | Отдел закупок отвечает на вопросы; онлайн-консультация раз в неделю. |

Показать вопросы о периоде/формате истории продаж и измеримом критерии успеха.
До ввода ответов неизвестные критерии и ограничения должны оставаться пустыми.

| Предложение | Идея | План | Срок |
|---|---|---|---|
| Команда А | Прогноз по дням недели и товарам | Изучить CSV, собрать базовый прогноз, проверить прошлые недели, показать прототип | 2026-10-15 |
| Команда Б | Прогноз с учётом выходных и сезонности | Проверить данные, сравнить два метода, провести тест с управляющим | 2026-10-22 |

Ссылки на прототипы добавить из подготовленных материалов; не выдавать заглушку URL
за готовое решение. Названия команд и предложения относятся к `teams`/`proposals`,
а не к входу ИИ при формировании бизнес-карточки.

## Поминутный план

| Время | Действия на экране | Реплика и видимое доказательство |
|---|---|---|
| **0:00–0:30** | Открыть главную, выбрать бизнес | «Студентам трудно начать с расплывчатой задачи. AI Sana помогает уточнить её, показывает готовность и открывает всем командам. Исполнителя выбирает бизнес». |
| **0:30–2:00** | 0:30–0:45: ввести черновик. 0:45–1:05: показать ≥3 вопроса, режим fallback и подготовленный промпт/JSON. 1:05–1:30: вставить ответы, собрать и отредактировать карточку. 1:30–2:00: явно подтвердить поля | Сначала **0/100**, затем **20 → 40 → 55 → 70 → 80 → 90 → 100**. Видны расшифровка и сокращение списка пробелов. Экран обновляется после PATCH без F5. «Факты сообщил бизнес; невалидный ответ API отбрасывается, есть локальный fallback». |
| **2:00–3:00** | Проверить название/контекст; нажать «Подтвердить и опубликовать»; открыть каталог; показать новую карточку среди задач со 100 баллами и опубликованную задачу с 20 баллами | «Полная постановка получает более высокую позицию. Низкий рейтинг не закрывает задачу студентам». При равном рейтинге порядок по id: новая карточка не обязательно первая. |
| **3:00–4:00** | 3:00–3:15: роль команды, фильтры HoReCa/«Приоритетная», сортировка. 3:15–3:45: открыть **ту же карточку**, отправить идею, план, срок и ссылку от А. 3:45–4:00: второй оператор отправляет Б через UI | «Команды сами выбирают интересную задачу». Оба предложения сохранены как `pending`, `chosen=0`; отправка не означает победу. |
| **4:00–4:45** | Бизнес сравнивает два предложения по идее, плану, сроку и прототипу; нажимает «Выбрать» у А и при желании «Отклонить» у Б | До клика нет выбранного исполнителя. Решение появляется у бизнеса и команды. «Можно выбрать одну, несколько или ни одной команды. Автоматического назначения нет». |
| **4:45–5:00** | Показать итоговые статусы, кратко указать на README и результаты тестов | «Показали уточнение задачи, прозрачные баллы, открытый каталог, отклики и ручное решение. Это демонстрирует сквозной сценарий, качество карточки, геймификацию, каталог и AI-функцию; запуск и тесты описаны в репозитории». |

## Критерии оценки из PDF

| Критерий | Максимум | Доказательство на защите |
|---|---:|---|
| Сквозной сценарий | 20 | Одна задача проходит все экраны и сохраняется в SQLite |
| Качество карточки | 15 | ≥3 уместных вопроса, редактируемые ответы, ручное подтверждение |
| Геймификация бизнеса | 25 | Прозрачные веса, пробелы, рост рейтинга и влияние на позицию |
| Каталог и отклики | 15 | Общая доступность, фильтры, предложения и ручные решения |
| AI-функция | 10 | Вопросы и структура без новых фактов; промпт, JSON, плохой ответ и fallback |
| Техническое качество | 10 | Запуск, API, валидация и воспроизводимые проверки |
| Демонстрация | 5 | Целостный работающий показ за 5 минут |
| **Всего** | **100** | Шкала жюри, отдельная от рейтинга карточки |

## Если что-то не сработало

При отказе внешнего AI продолжить через fallback и назвать режим. При ошибке
валидации исправить ввод; не обходить подтверждения и не менять БД вручную.
Если интеграция UI/API не работает, прямо обозначить незавершённый участок.
Отдельные API-запросы, LocalStorage-демо или ролик не заменяют требуемый живой
сквозной сценарий; резервные материалы служат для пояснения, а не скрытия ошибки.
