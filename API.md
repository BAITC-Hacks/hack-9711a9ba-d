# AI Sana: backend API

## Запуск и обновление

Требуются PHP 8.2+ и расширение `pdo_sqlite`; для внешнего ИИ также нужен `curl`.
Из корня проекта:

```powershell
php seed.php
php -S 127.0.0.1:8000 router.php
```

seed.php создаёт или обновляет схему. В пустую БД добавляется по 5 записей каждой
сущности. При наличии хотя бы одной записи seed пропускается. Для обновления
существующей БД без демо-данных: `php migrate.php`. Повторная миграция безопасна;
существующие данные, идентификаторы и принятые предложения сохраняются.
Миграция версии 1 также исправляет рейтинг пустых подтверждённых полей и
синхронизирует статус черновика с наличием опубликованных карточек.

Если php отсутствует в PATH:

```powershell
& '.\.tools\php\php.exe' seed.php
& '.\.tools\php\php.exe' -S 127.0.0.1:8000 router.php
```

Пример выше подходит, если локальный PHP установлен в `.tools/php`; иначе укажите
путь к своему `php.exe`. База `database.sqlite` находится рядом с `db.php`.
`seed.php` и `migrate.php` доступны только через CLI. Интерфейс:
http://127.0.0.1:8000/; каталог API: http://127.0.0.1:8000/api/catalog.php.
Используйте `router.php`: он разрешает только публичные API и файлы `frontend/`,
закрывая доступ к БД, `.env`, тестам и служебным PHP-файлам.

## Общие правила

POST/PATCH принимают JSON-объект с Content-Type: application/json; параметр
`charset=UTF-8` разрешён, регистр типа не важен. Ответы и ошибки
всегда JSON; списки — массивы, отдельные сущности — объекты. Создание — HTTP 201,
чтение/изменение — 200. Ошибки: 400 (валидация), 404 (нет записи), 405 (метод),
409 (предложение по неопубликованной карточке), 415 (отсутствует или не подходит
Content-Type), 422 (небезопасный или невалидный
ввод ИИ-помощника), 500 (внутренняя ошибка), 502 (некорректный результат помощника,
который нельзя сохранить). Формат ошибки: {"error":"сообщение"}. Все API поддерживают OPTIONS,
но не разрешают CORS: frontend и API работают с одного origin. Запросы используют подготовленные SQL-выражения.
Текстовые значения — строки UTF-8 до 12000 байт без управляющих символов; пробелы
по краям удаляются. Идентификаторы — положительные целые числа. Флаги принимают
`0`, `1`, `false`, `true`, но не строки `"0"`/`"1"`.

## Черновики и уточняющие вопросы

- `POST /api/tasks.php`: `{"raw_description":"Нужен прогноз спроса для кафе"}` → `{"task_id":6}`.
- `GET /api/tasks.php?id=6`: черновик. Без id — список всех черновиков/задач, новые первыми.
- `GET /api/questions.php?task_id=6`: от трёх до семи вопросов, `provider` и `rating_details`.
- `POST /api/questions.php`: `{"task_id":6,"card_id":6}` — вопросы по текущей карточке;
  card_id необязателен, принадлежность черновику проверяется. GET поддерживает те же параметры.

Вопросы сначала относятся к пустым и неподтверждённым полям. Если все поля заполнены
и подтверждены, возвращаются три вопроса для проверки актуальности. Каждый вопрос
содержит `field`, `question`, `reason` (`empty`, `not_confirmed` или `review`).
Список необходимых полей определяет сервер; внешняя модель может сформулировать
вопросы, но не изменить этот список. Запрос не создаёт карточку и не меняет рейтинг.

## Формирование и редактирование карточки

`POST /api/generate.php`:

```json
{
  "task_id": 6,
  "answers": {
    "title": "Прогноз спроса для кафе",
    "topic": "HoReCa",
    "need": "Уменьшить списания",
    "data_materials": "CSV продаж за шесть месяцев",
    "expected_result": "Прототип прогноза на завтра"
  }
}
```

Ответ: `{"provider":"local_stub","fallback_reason":"not_configured","card_id":6,"card":{...},"questions":[...]}`.
При успешном внешнем запросе `provider` равен `openai`, а `fallback_reason` отсутствует.
`answers` — JSON-объект; `{}` или отсутствие `answers` допустимы. Разрешены семь
оцениваемых полей и `title`, `topic`, `need`, `interaction_format`.
Создаётся новая неопубликованная карточка с рейтингом 0 и всеми подтверждениями 0.
context по умолчанию содержит исходное описание дословно; answers.context может его
заменить. Неизвестные факты остаются пустыми. Каждый POST создаёт новую карточку.
Чтобы редактировать существующую, используйте PATCH cards.php.
Возвращаемые после сборки `questions` — локальные вопросы проверки новой карточки;
`provider` относится к её формированию.

Совместимый интерфейс через `POST /api/cards.php`:

- `{"action":"questions","task_id":6}` → `task_id`, `questions`, `provider` и, при
  fallback, `fallback_reason`. Вопросы содержат `field` и `question`; здесь нет
  `reason` и `rating_details`, выбор полей основан на исходном описании.
- `{"action":"build","task_id":6,"answers":{"title":"Прогноз спроса","users":"Управляющий кафе."}}`
  → HTTP 201, `card_id`, полная `card`, `provider` и, при fallback, `fallback_reason`.
  Для этого вызова `answers` обязателен и должен быть JSON-объектом.

Оба пути используют один ИИ-помощник и серверное описание из сохранённой задачи.

`POST /api/cards.php` по-прежнему создаёт карточку напрямую: `{"task_id":6}` плюс
любые из 11 текстовых полей, без `action`. Ответ содержит `card_id` и полную `card`;
провайдер не вызывается. Подтверждения, рейтинг и публикация с клиента не принимаются.
`GET /api/cards.php?id=6` возвращает карточку и rating_details.

`PATCH /api/cards.php`:

```json
{"id":6,"field":"data_materials","value":"CSV продаж за шесть месяцев","confirmed":1}
```

Семь оцениваемых полей: context, data_materials, expected_result, success_criteria,
constraints, users, business_contact. Для них confirmed по умолчанию равен 1
(совместимость с первым API). `confirmed:0` сохраняет черновое значение или снимает
подтверждение; пустой текст разрешён только при confirmed=0. id можно передать в URL.
Дополнительно редактируются title, topic, need, interaction_format; у них нет отдельного
confirmed и дополнительных баллов. Потребность также должна быть отражена в context,
а порядок обратной связи — в business_contact, чтобы критерии рейтинга были содержательными.

Любое фактическое изменение карточки снимает её с публикации до повторной проверки.
Повторный PATCH с тем же текстом и подтверждением публикацию не меняет.
Рейтинг, текст и подтверждение обновляются атомарно.

## Рейтинг

Баллы начисляются только за непустой текст с confirmed=1: context=20,
data_materials=20, expected_result=15, success_criteria=15, constraints=10,
users=10, business_contact=10. Уровни: 0–39 «проект», 40–69 «в работе»,
70–89 «готово», 90–100 «приоритет».

calculateRating() сохраняет контракт `{rating, level}`. Дополнительный ratingDetails()
и поле ответа rating_details содержат breakdown (вес, начисленные баллы, заполненность,
подтверждение) и missing_fields (причина, действие, потенциальные баллы).

## Ручная публикация и каталог

`PATCH /api/publish.php`: `{"card_id":6,"published":1,"confirmed":1}`.
confirmed означает, что человек просмотрел и подтвердил карточку целиком для публикации.
Он не меняет отдельные подтверждения полей и не добавляет баллы. Требуются непустые
title и context. Порог рейтинга отсутствует: публикация разрешена даже при 0 баллов.
Снять с публикации: `{"card_id":6,"published":0}`. Статус исходной задачи обновляется
в той же транзакции: published, если есть хотя бы одна её опубликованная карточка.

`GET /api/catalog.php?sort=rating&topic=образование&level=приоритет`.
Только published=1, по умолчанию сортировка rating DESC, id ASC. Фильтры сочетаются.
topic ищет подстроку в title, topic, need и шести содержательных полях карточки,
без контакта бизнеса; поиск регистронезависимый, включая кириллицу.
level — точное русское название уровня. Кодируйте параметры URL.
В новой демо-базе опубликованы карточки с рейтингами 20, 40, 70, 90, 100.

## Команды, предложения и ручное решение

- `POST /api/teams.php`: `{"name":"AI Team","interests":"EdTech","skills":"NLP","technologies":"Python, PHP"}` → team_id.
- `GET /api/teams.php`: список команд; `GET /api/teams.php?id=1` — отдельный профиль.
- `PATCH /api/teams.php`: `{"id":1,"skills":"NLP, SQL","technologies":"Python, PHP"}`
  → обновлённый профиль. Допускаются `name`, `interests`, `skills`, `technologies`;
  требуется хотя бы одно поле, пропущенные сохраняются. `name` не может быть пустым.
  Идентификатор также можно передать в URL.
- `POST /api/proposals.php`: `{"card_id":6,"team_id":1,"solution_idea":"Прогноз по дням недели","plan":"Анализ, прототип, проверка","prototype_link":"","deadline":"2026-10-15"}` → proposal_id.
- `GET /api/proposals.php?card_id=6`: предложения по карточке с `chosen`, `status`,
  `team_name` и `card_title`.
- `GET /api/proposals.php?team_id=1`: предложения одной команды. Можно передать оба
  фильтра: тогда применяются одновременно. Без `card_id` и `team_id` возвращается 400.

Предлагать решение можно любой опубликованной карточке независимо от рейтинга.
Количество предложений не ограничивается. Ссылка — HTTP/HTTPS или пустая строка;
deadline — существующая дата YYYY-MM-DD. Начальное состояние pending, chosen=0.

`PATCH /api/choose.php`: `{"proposal_id":6,"decision":"accepted"}`.
accepted — принять (chosen=1); rejected — отклонить (chosen=0); pending — отменить
решение (chosen=0). Без decision сохраняется старый вызов «принять» по proposal_id.
Решения по другим предложениям НЕ сбрасываются: бизнес может выбрать несколько команд.
Любое изменение решения — только явный вызов этого API; рейтинг и помощник не выбирают команды.

## ИИ и локальный резервный режим

`ai_helper.php` подключён к обоим путям генерации. Без `AI_API_KEY` используется
детерминированный `local_stub`, который не вызывает языковую модель. Для внешнего
режима скопируйте `.env.example` в `.env` и задайте ключ; `AI_MODEL` по умолчанию —
`gpt-4o-mini`. PHP загружает эти две настройки из `.env`; переменные окружения имеют
приоритет, в том числе явно пустой ключ. Ключ остаётся на сервере.

При доступном ключе и cURL используется OpenAI Responses API. Публичное поле `provider`
отражает фактически использованный результат: `openai` или `local_stub`.
В резервном режиме `fallback_reason` равен одному из значений:

| Значение | Причина |
| --- | --- |
| `not_configured` | Ключ не задан |
| `curl_unavailable` | Расширение cURL недоступно |
| `provider_unavailable` | Ошибка подключения, тайм-аут или неуспешный HTTP-ответ |
| `invalid_response` | Ответ провайдера не соответствует формату или проверкам |

Ошибки провайдера переключают на локальную обработку. До сохранения проверяются
структура и совпадение каждого из семи содержательных полей с его исходным ответом;
помощник не дописывает факты и не подтверждает поля. Небезопасный ввод помощника
возвращает 422 без создания карточки. Ошибки типов и неизвестные поля обычных API
возвращают 400. Подробные контракты, ограничения и тесты: [AI_HELPER.md](AI_HELPER.md).

## Демонстрационный сценарий

1. Создать слабый черновик через tasks.php.
2. Получить вопросы через questions.php.
3. Передать ответы в generate.php и получить неопубликованную карточку с рейтингом 0.
4. Подтвердить поля через PATCH cards.php, показать начисленные и недостающие баллы.
5. Опубликовать через publish.php, найти карточку в каталоге.
6. Отправить предложения от двух команд.
7. Вручную принять оба, затем отклонить одно: другое остаётся принятым.

## Фронтенд и границы MVP

Фронтенд из `frontend/` обращается к этим HTTP API: карточки, профили команд,
предложения, решения и рейтинг сохраняются в SQLite. Переключение роли в интерфейсе
не является авторизацией: API пока не проверяет личность, роль отправителя или
владельца карточки. Регистрация/вход, разграничение доступа, чат, уведомления,
баллы командам за прогресс и обучение собственной модели остаются отдельными этапами.
`router.php` ограничивает статическую раздачу при локальном запуске; при развёртывании
на другом веб-сервере нужны эквивалентные ограничения и авторизация.

Фронтенд использует имена полей API (`topic`, `data_materials`, `expected_result`,
`success_criteria`, `business_contact`, `interaction_format`, `rating`). Backend
возвращает целочисленные id; задача (`task_id`) и карточка (`card_id`) — разные
сущности. В предложении используется
конкретная дата `deadline`, а `#` не является допустимой ссылкой. Рейтинг,
подтверждения, публикацию и решения возвращает сервер.

## Тесты

`php tests/rating_test.php` — все 128 комбинаций подтверждений, границы уровней,
пустые/неподтверждённые поля, валидация помощника.
`python tests/api_test.py` — запуск собственного временного сервера и отдельной
базы, HTTP-контракты и миграция старой схемы без изменения рабочей БД.
